Add an Admin Inventory Manager area to this existing Wine Pairing app.

CRITICAL CONSTRAINTS
- Admin users must ONLY be able to manage restaurant data: menu items and wine items.
- Admin users must NOT be able to change the UI/theme, pairing logic, scoring formula, or any global content/templates.
- Admin UI must be minimal and use existing components (shadcn/ui) and existing theme tokens.
- Do NOT introduce any “CMS” features or free-form page editing.

SCOPE
Admin can:
1) Login (secure)
2) View list of menu items and wine items
3) Add new menu/wine items
4) Edit existing menu/wine items (specific fields only)
5) Mark items as Out of Stock (toggle)
6) Label items (e.g., “Seasonal”, “New”, “Chef’s special”, “By the glass”)
7) Changes affect what appears to regular users:
   - Out of stock items are hidden from pairing suggestions OR clearly marked as unavailable (use a consistent rule)
   - Pairing results must not include out-of-stock wines by default

Admin cannot:
- Edit any UI copy outside item fields
- Upload custom CSS/theme values
- Modify scoring logic settings or weights
- Modify “wine description generator” templates
- Modify app navigation (except adding Admin route)
- Modify any user-facing static text beyond menu/wine item fields

3) AUTH: ADMIN LOGIN ONLY
------------------------------------------------------------
Implement admin auth with these rules:

- Single Admin role only: role = "admin"
- Admin accounts are created via:
   OPTION A (preferred): environment variable bootstrap (ADMIN_EMAIL + ADMIN_PASSWORD) to create first admin on startup
   OPTION B: a one-time CLI/seed script in repo to create admin
- Password hashing must use bcrypt or argon2.
- Login returns a session cookie (httpOnly, secure where applicable) or JWT stored in httpOnly cookie.
- Protect all /admin API routes with requireAdmin middleware.
- Rate limit login attempts (basic) and return generic errors (no user enumeration).

DO NOT add “sign up” UI for the public.

------------------------------------------------------------
4) BACKEND ROUTES (ADMIN ONLY)
------------------------------------------------------------
Create admin endpoints:

POST   /api/admin/login
POST   /api/admin/logout
GET    /api/admin/me

Menu:
GET    /api/admin/menu
POST   /api/admin/menu
PATCH  /api/admin/menu/:id
PATCH  /api/admin/menu/:id/out-of-stock   (toggle)
PATCH  /api/admin/menu/:id/labels         (replace labels)

Wine:
GET    /api/admin/wines
POST   /api/admin/wines
PATCH  /api/admin/wines/:id
PATCH  /api/admin/wines/:id/out-of-stock
PATCH  /api/admin/wines/:id/labels

Validation:
- Validate inputs (zod/yup/joi depending on stack).
- Restrict editable fields to the ones listed above.
- Reject unknown fields to prevent UI/template injection.

------------------------------------------------------------
5) USER-FACING BEHAVIOR (OUT OF STOCK)
------------------------------------------------------------
Decide and implement this consistent behavior:
- Default: out-of-stock wines MUST NOT appear in pairing results.
- If user is viewing a wine list screen, out-of-stock wines can either:
   A) be hidden, OR
   B) shown with an “Out of stock” badge and disabled selection.
Choose ONE approach and apply consistently.

Menu out-of-stock:
- out-of-stock dishes should either be hidden OR shown disabled (choose one, consistent).
